# VAHDAM DTC Data Engine — Replication Guide

**Purpose:** Offline Python ETL engine that ingests VAHDAM's DTC source systems (Matrixify/Shopify, Shopify Analytics, Klaviyo, WebEngage) into a local DuckDB warehouse, then syncs aggregated fact tables to Supabase Postgres for the lifecycle dashboards.

- **Last updated:** 2026-06-20
- **Deploy target:** N/A — this is a **local/offline batch engine**, not a deployed service. It runs on a developer/analyst machine (or a scheduled box/cron). Its *output* (Supabase `dtc.*` fact tables) is what the deployed Vercel app reads. Slated to be absorbed into **Vahdam-LifeCycle-OS** `/data` module (see §7).

> **Authoring note:** This guide was written from the canonical engine sources as they exist in the `Vahdam-LifeCycle-OS` repo (`ingest/`, `run_all.py`, `sync_to_supabase.py`, `VAHDAM_DuckDB_DDL.sql`) — the same files this standalone project is built from and that LifecycleOS will migrate per its `docs/UNIFIED-ARCHITECTURE.md` §8. If this standalone repo's copies diverge, the local files are the source of truth — diff them against this guide.

## 1. Current-state snapshot — what it does now

A four-stage offline pipeline:

```
 CSV/JSON exports          DuckDB warehouse            Supabase Postgres
 (data/<source>/)   ──▶    vahdam_dtc.duckdb    ──▶    dtc.fact_*  (+ dtc.sync_log)
   matrixify/              4 schemas / 46 tables        consumed by the dashboards
   shopify_analytics/      (VAHDAM_DuckDB_DDL.sql)      (realtime subscribers update live)
   klaviyo/
   webengage/
```

**Stage A — Source ingestion** (`run_all.py` orchestrates 4 loaders in `ingest/`):
- `ingest_matrixify.py` — raw Shopify export CSVs → `matrixify.*`. **Upsert** by `id` (DELETE-then-INSERT). Knows 20 tables (orders, customers, products, product_variants, discounts, order_line_items, collections, etc.). JSON-typed columns (line_items, addresses, metafields, …) coerced to string. Date columns (`*_at`, `*_date`, `date`) parsed to tz-naive UTC.
- `ingest_shopify_analytics.py` — Shopify Analytics report CSVs → `shopify_analytics.*`. **Append + dedup** on `(report_date, report_period)`; synthesizes an `id` if absent. Knows 13 tables (revenue_metrics, acquisition_metrics, customer_cohorts, product_performance, …).
- `ingest_klaviyo.py` — Klaviyo CSV **or** JSON → `klaviyo.*`. Per-table strategy in `TABLE_CONFIG`: `upsert` (profiles, campaigns, flows, lists, segments, sms_metrics, deliverability, profile_growth) or `append` (events). JSON cols (custom_properties, event_properties, subscriptions, definition) json.dumps'd.
- `ingest_webengage.py` — WebEngage CDP CSVs → `webengage.*` (user_profiles upsert, events append, revenue_mapping upsert). **After loading events, auto-rebuilds `webengage.event_summary`** (daily roll-up by event_name+channel: counts, unique_users, total_revenue).

All loaders share the same pattern: clean column names (`lower`, spaces→`_`, strip non-`[a-z0-9_]`), parse dates, keep only columns that already exist in the target table (`information_schema.columns`), stamp `_loaded_at`, encode-fallback `utf-8`→`latin-1`. Each `ingest()` returns `{table: rowcount}`. `run_all.py` logs to `logs/ingest_<timestamp>.log`, supports `--source <name>` to run one loader, and prints a per-source row/elapsed summary.

**Stage B — Supabase sync** (`sync_to_supabase.py`): opens DuckDB read-only, runs 5 aggregation SQL queries, and **upserts** results into 5 Supabase `dtc.fact_*` tables via `psycopg2` `execute_batch` with `ON CONFLICT … DO UPDATE`. Writes a row to `dtc.sync_log` per job. Jobs:

| DuckDB query | → Supabase table | conflict key |
|---|---|---|
| daily orders (matrixify.orders ⨝ customers, 180d) | `dtc.fact_daily_orders` | (market, order_date) |
| channel perf (shopify_analytics.acquisition_metrics, weekly, 180d) | `dtc.fact_channel_perf` | (channel, market, period_start) |
| cohort retention (shopify_analytics.customer_cohorts, 12mo) | `dtc.fact_cohort_retention` | (cohort_month, market) |
| Klaviyo flow perf (klaviyo.flow_performance, weekly, 180d) | `dtc.fact_klaviyo_perf` | (flow_id, period_start) |
| top products (shopify_analytics.product_performance, 30d, top-20/market) | `dtc.fact_top_products` | (period_start, market, sku) |

Computes derived metrics in-SQL: net_revenue, AOV, discount_pct, CAC, ROAS, LTV, repeat_rate_90d, open/click rates, rev_per_send.

**Recent progress / state:** Sample seed CSVs are present under `data/<source>/` (matrixify: 6 files, shopify_analytics: 6, klaviyo: 4, webengage: 2), so the pipeline runs end-to-end against demo data out of the box. The engine is being folded into LifecycleOS's `/data` module (Phase 4 of the unified plan).

## 2. Clone-to-exact-state runbook

> Pure-Python; no Node build, no Vercel deploy. DuckDB file is local and gitignored — regenerated by running the pipeline.

```bash
# 0. Clone / open this directory
cd vahdam_dtc_data_engine

# 1. Python env (3.9+). The scripts import: duckdb, pandas, psycopg2.
python3 -m venv .venv && source .venv/bin/activate
pip install duckdb pandas psycopg2-binary
#   (If a requirements.txt exists in this repo, prefer:  pip install -r requirements.txt)

# 2. Create the DuckDB warehouse schema (4 schemas, 46 tables).
#    The DDL file is VAHDAM_DuckDB_DDL.sql. Apply it once:
duckdb vahdam_dtc.duckdb ".read VAHDAM_DuckDB_DDL.sql"
#    DB_PATH is hardcoded to <repo>/vahdam_dtc.duckdb in every loader.

# 3. Drop source exports into the expected folders (filename == table name):
#    data/matrixify/*.csv          (orders.csv, customers.csv, products.csv, …)
#    data/shopify_analytics/*.csv  (revenue_metrics.csv, acquisition_metrics.csv, …)
#    data/klaviyo/*.csv|*.json     (profiles.*, campaigns.*, flows.*, events.*, …)
#    data/webengage/*.csv          (user_profiles.csv, events.csv, revenue_mapping.csv)
#    Files whose basename is not a KNOWN_TABLE/TABLE_CONFIG entry are skipped with a warning.

# 4. Run ingestion (all sources, or one).
python run_all.py                      # all four loaders, logs to logs/
python run_all.py --source klaviyo     # just one source

# 5. Sync aggregates to Supabase (requires the dtc.* tables to already exist there).
export SUPABASE_DATABASE_URL="postgres://...."   # Supabase → Settings → Database → Connection string
export DUCKDB_PATH="vahdam_dtc.duckdb"           # optional; defaults to ./vahdam_dtc.duckdb
python ingest/sync_to_supabase.py
```

Re-running is **idempotent** for upsert tables (DELETE+INSERT / ON CONFLICT). Append tables (`*.events`) use `INSERT OR IGNORE` keyed on the configured id, so re-loading the same export won't duplicate.

There is **no test suite, no lint, no build step** in this engine. Verification = inspect the log summary and query the DuckDB file (`duckdb vahdam_dtc.duckdb "select count(*) from matrixify.orders"`).

## 4. Domain knowledge / data model a cloner must know

**DuckDB warehouse — `vahdam_dtc.duckdb`, defined by `VAHDAM_DuckDB_DDL.sql` (4 schemas, 46 tables):**
- **`matrixify`** — raw Shopify objects via Matrixify exports. ~20 tables: `orders`, `order_line_items`, `customers`, `products`, `product_variants`, `discounts`, `smart_collections`, `custom_collections`, `companies`, `draft_orders`, `payouts`, `pages`, `blog_posts`, etc. PK = Shopify `id`; nested objects stored as DuckDB `JSON`.
- **`shopify_analytics`** — pre-aggregated report tables (13): `revenue_metrics`, `orders_by_status`, `traffic_metrics`, `conversion_funnel`, `acquisition_metrics`, `device_metrics`, `geography_metrics`, `customer_metrics`, `customer_cohorts`, `product_performance`, `collection_performance`, `marketing_attribution`, `discount_usage`. Time-bucketed; deduped on `(report_date, report_period)`.
- **`klaviyo`** — email/SMS engagement: `profiles`, `profile_growth`, `campaigns`, `flows`, `sms_metrics`, `lists`, `segments`, `events` (append), `deliverability`. (Note: `sync_to_supabase.py` queries `klaviyo.flow_performance` — ensure that table/view exists if you use that job.)
- **`webengage`** — CDP: `user_profiles`, `events` (append), `revenue_mapping`, and the derived `event_summary` (auto-rebuilt from events on each WebEngage ingest).
- Every table carries `_loaded_at TIMESTAMP DEFAULT current_timestamp`.

**Source systems → loader → strategy:**
| Source | Format | Loader | Strategy |
|---|---|---|---|
| Matrixify (raw Shopify) | CSV | `ingest_matrixify.py` | upsert by `id` |
| Shopify Analytics | CSV | `ingest_shopify_analytics.py` | append + dedup `(report_date, report_period)` |
| Klaviyo | CSV or JSON | `ingest_klaviyo.py` | per-table upsert/append (`TABLE_CONFIG`) |
| WebEngage | CSV | `ingest_webengage.py` | upsert/append + rebuild `event_summary` |

**Supabase target — `dtc` schema (lives in the Supabase project, NOT in this repo's files):** 5 fact tables (`fact_daily_orders`, `fact_channel_perf`, `fact_cohort_retention`, `fact_klaviyo_perf`, `fact_top_products`) + `sync_log`. These must be **created in Supabase before sync** (the engine does not migrate Supabase; it only upserts). Markets are inferred from `shipping_address->>'country_code'` / analytics `market` column, defaulting to `Global`/`Unknown`. Dashboards subscribe to these tables via Supabase Realtime, so a sync immediately updates live charts.

**Conventions:** column names normalized to snake_case; dates coerced to tz-naive UTC; JSON columns stringified; encoding fallback utf-8→latin-1; only columns already present in the target table are inserted (extra export columns are silently dropped).

## 5. Common pitfalls

1. **Run the DDL first.** Loaders only insert into columns that already exist (`information_schema.columns`); against an empty/missing schema every load returns 0 rows with no hard error. Apply `VAHDAM_DuckDB_DDL.sql` before the first ingest.
2. **Filename = table name.** A CSV/JSON whose basename isn't in the loader's `KNOWN_TABLES`/`TABLE_CONFIG` is skipped with a "Skipping unknown table file" warning, not loaded.
3. **`dtc.*` tables must pre-exist in Supabase.** `sync_to_supabase.py` does not create them; a missing table makes the job fail/skip.
4. **`klaviyo.flow_performance`** is queried by the sync but is not one of the loader's `TABLE_CONFIG` tables — it must exist as a table or view, or that one sync job is skipped (the script logs and continues).
5. **`SUPABASE_DATABASE_URL` is the Postgres connection string**, not the project REST URL or anon key. Wrong value → psycopg2 connection error.
6. **DuckDB single-writer lock.** Don't run two ingest processes against `vahdam_dtc.duckdb` simultaneously; sync opens it `read_only=True` so it can run alongside readers but not a concurrent writer.
7. **Append tables dedup by configured key only.** `events` tables use `INSERT OR IGNORE` on their id column — exports lacking stable ids get synthesized hash ids per-row and can duplicate across runs.
8. **Encoding.** Non-UTF-8 exports are retried as latin-1; truly broken files raise "Cannot decode/read".

## 6. Where to look next

- **`VAHDAM_DuckDB_DDL.sql`** — authoritative warehouse schema (read top-to-bottom for exact columns).
